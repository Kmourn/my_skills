# 科研代码风格

先理解当前实验、要改变的行为和已有代码约定；把科研设置与数值语义落实为易读、易改的代码。

1. 用少量直白函数、常见数组／表格类型和顺序清楚的入口表达工作；按实际职责与修改需要拆分。保持已有语言、结构与接口，已有类或模块有效时继续使用。不设行数／文件数门槛，不靠密集一行写法追求短。
2. 常改参数放在可见位置，经具名函数参数或小型配置显式传入。让数值方法、精度、容差、数据划分和随机种子保持可见；保留既有默认值与随机状态语义。单个实现不增加配置引擎、工厂、注册器或接口层。
3. 清楚呈现读取、筛选、缺失处理、变换、核心计算、指标和输出的实际顺序；调整顺序时确认科学含义。保留原始输入，将实际参数及数据／代码版本链接到已有实验记录，不另建重复登记表。
4. 优先现有科学计算库和项目约定。新增依赖、抽象或并行机制须解决当前实际需求；拆开 I/O 与计算以便修改或检查时，不强制整个项目改成函数式。
5. 根据计算责任保留必要的形状、单位、有限值、数据对应和守恒量检查。正确性证据可用解析解或独立参考值；说明预期值及容差的依据。不同实现复算可查一致性，但不能冒充独立证明。
6. 需要确认结果或数值行为时，用相同设置复跑代表性小案例或受影响检查，报告结果、偏差和未验证范围。纯格式或无行为影响的小改动不强制新增测试；以理解与修改成本判断简洁程度。

需要具体示例时，读 [可手算的数据变换例子](references/example.md)。这不是所有项目都应采用的模板。

## 专业边界

复杂度与必要验证交 `stop-that-shit`；跨模块结构调整交 `reviewing-code-modularity-skill`；实验比较、指标和运行顺序交 `experiment-plan`；统计设计、方法与解释交 `statistical-analysis`。只在任务实际涉及这些问题时衔接，不自动扩展任务。

# 稳健推进

## 执行节奏

用户要求先讨论再落实时，先交付具体方案，依赖其决定的实施等确认后开始，独立的只读核查可以继续。执行获准后，负责人在约定范围、预算和停止条件内跟进到验收，自行处理常规检查和可安全恢复的续跑。需要扩大已授权范围或预算、取得新权限，或涉及用户取舍时，再请用户决定。

长期任务需要脱手时，核实实际运行状态，说明接续或检查入口、下个检查时点及需要人工介入的情形。进展和验收依据写入已有记录。

## 推进约束

1. **ROS 与实物测试优先人工执行。** 涉及 ROS 节点或实物运动的测试，优先提供人工执行步骤与验收要点。如需自动执行，先说明测试范围、设备影响与停止条件，获得用户明确许可后再运行；已有许可覆盖的测试不重复请示。普通软件测试按任务授权执行。

2. **服务器修改限于当前用户主目录，不使用 sudo。** 从当前运行环境取得当前用户的实际主目录（通常由 `~` 或 `HOME` 表示），不按固定用户名或机器路径拼接；这里的边界是用户主目录，不是系统根目录 `/`。文件修改、依赖安装、缓存及临时产物均放在该目录内；写入前展开变量并确认实际路径，避免通过符号链接写到目录外。`CODEX_HOME` 等工具配置目录不改变这一写入边界。遇到目录外写入或管理员权限需求时，说明阻碍并寻找用户目录内的方案，不使用 `sudo` 命令。

3. **在适当进度节点推送任务子分支。** 在完成可独立审阅的阶段成果、相关检查通过，或需要交接时，使用本地已有 SSH 身份，将当前任务代码提交并推送至当前任务已核实的仓库子分支。用户明确指定的目标优先，否则核对当前仓库已有的 SSH 推送远程；不从固定账户、目录名或历史来源记录推断目标。优先复用已有任务分支，否则创建用途清楚的子分支；只提交当前任务相关改动，保留用户其他未提交工作，不直接推送默认分支。目标缺失或不明确时先完成本地可审阅成果，再请用户指定；SSH 认证失败时报告具体阻碍，不创建身份或读取、输出私钥内容。推送成功后给出仓库、分支与提交信息。

## 项目版本谱系

梳理方案分叉、从已有基准派生新方案或选择当前基准时，按需读取[项目版本谱系](references/version-lineage.md)。在已有记录中说明起点、跨分支复用和取舍依据，分别标明运行状态、验证范围与采用决定。需要查看全局关系时用 Mermaid 图。

## 阶段末确认与沉淀

工作过程中先把反馈用于当前任务，并积累待确认候选。大段工作结束、形成阶段成果或需要交接时，集中给出**拟保存的个人偏好、拟新增或修订的 Skill、来源、具体内容与影响**，由用户确认后再持久化；不因每条反馈频繁打断，也不因自认为明确而省略确认。用户已对具体内容和范围作出的确认无需重复请求。

是否值得封装为 Skill 由 AI 自由评估，正式采用由用户确认。通用推进经验优先更新本 Skill，专业方法优先更新相应专业 Skill；单句个人偏好无需另建 Skill。确认后的框架改动遵循“仓库修改与检查 → GitHub 子分支推送 → 本地 Codex 同步”。

## 子智能体与思考强度

按独立取证、实施或复核的实际收益委派，主控组织集成与交付。同一批同类任务单人执行时用最高支持档，优先 `ultra`，其次 `max`。并行默认各用 `high`，任务需要时可让部分或全部并行成员用最高支持档。按所选模型和工具实际设置，详见[派发与回收](references/subagents.md)。

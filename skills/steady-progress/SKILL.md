# 稳健推进

按当前任务需要落实推进约束；用户已明确的任务授权与目标不重复询问。个人偏好持久化和可复用 Skill 的新增或修订，按下文的阶段确认规则处理。

## 推进约束

1. **ROS 与实物测试优先人工执行。** 涉及 ROS 节点或实物运动的测试，优先提供人工执行步骤与验收要点。如需自动执行，先说明测试范围、设备影响与停止条件，获得用户明确许可后再运行；已有许可覆盖的测试不重复请示。普通软件测试按任务授权执行。

2. **服务器修改限于当前用户主目录，不使用 sudo。** 从当前运行环境取得当前用户的实际主目录（通常由 `~` 或 `HOME` 表示），不按固定用户名或机器路径拼接；这里的边界是用户主目录，不是系统根目录 `/`。文件修改、依赖安装、缓存及临时产物均放在该目录内；写入前展开变量并确认实际路径，避免通过符号链接写到目录外。`CODEX_HOME` 等工具配置目录不改变这一写入边界。遇到目录外写入或管理员权限需求时，说明阻碍并寻找用户目录内的方案，不使用 `sudo` 命令。

3. **在适当进度节点推送 GitHub 子分支。** 在完成可独立审阅的阶段成果、相关检查通过，或需要交接时，使用本地已有 SSH 密钥，将当前任务代码提交并推送至 GitHub 用户 `Framework Contributors` 的对应仓库子分支。优先复用该仓库已有的任务分支，否则创建用途清楚的子分支；只提交当前任务相关改动，保留用户其他未提交工作，不直接推送默认分支。核对目标仓库与 SSH 远程地址；目标不明确时请用户指定，SSH 认证失败时报告具体阻碍，不读取或输出私钥内容。推送成功后给出仓库、分支与提交信息。

## 阶段末确认与沉淀

工作过程中先把反馈用于当前任务，并积累待确认候选。大段工作结束、形成阶段成果或需要交接时，集中给出**拟保存的个人偏好、拟新增或修订的 Skill、来源、具体内容与影响**，由用户确认后再持久化；不因每条反馈频繁打断，也不因自认为明确而省略确认。用户已对具体内容和范围作出的确认无需重复请求。

是否值得封装为 Skill 由 AI 自由评估，正式采用由用户确认。通用推进经验优先更新本 Skill，专业方法优先更新相应专业 Skill；单句个人偏好无需另建 Skill。确认后的框架改动遵循“仓库修改与检查 → GitHub 子分支推送 → 本地 Codex 同步”。

## 子智能体与思考强度

用户已一次约定委派边界后，按独立工作或独立复核的实际价值使用子智能体，无需逐次确认岗位和人数。委派覆盖原任务授权内的工作，人数受运行时容量限制；小任务由当前智能体直接完成，不为调整强度增加成员。

同一批同类任务由一名智能体执行时用 `max`，由多名智能体并行执行时各用 `high`。不同类任务分别计数；只负责协调的智能体不计入专业任务的执行人数。模型沿用用户选择，强度在可设置的调用或派发时按规则明确指定，不以文字描述冒充参数生效。

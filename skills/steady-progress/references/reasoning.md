# high／max 指派规则

仅按同一批同类任务的实际执行人数指派，不再按任务难度、调研阶段或成员身份分档：

| 执行方式 | 指派强度 |
| --- | --- |
| 一名智能体执行，包括多人串行但同一时段只有一名执行者 | `max` |
| 多名智能体并行执行 | 每名执行者 `high` |

“同类任务”按工作功能划分，例如检索、实施、复核；不同类任务分别计数。只协调和汇总的智能体不计入专业任务的执行人数，若亲自执行专业任务则计入该类。协调任务自身只有一名执行者时同样指派 `max`。

例如：

- 一个智能体完成调研检索：`max`。
- 两个检索成员同时调查同一调研任务的不同资料来源：均为 `high`。
- 一个成员检索、另一个成员实施：两类各只有一名执行者，均为 `max`。
- 多个实施成员并行处理不同模块：该批实施成员均为 `high`。

先根据独立工作价值决定是否拆分，再按人数指派；不为降低强度而增加成员或人为拆类。调研检索与其他工作遵循同一规则。

## 设置与生效

1. 在规划执行批次时确定分组和强度，在可设置参数的调用或派发时明确传入 `max` 或 `high`。模型沿用用户选择，并核对该模型与客户端支持这两档。
2. 子智能体使用派发工具实际提供的强度参数，不依赖父级强度恰好符合本批规则。若上下文继承方式与覆盖参数冲突，选择支持覆盖的方式，并补齐用户选择、任务边界、资料路径和必要上下文。
3. 当前环境的 `collaboration.spawn_agent` 完整历史继承（`fork_turns="all"` 或省略）不能覆盖强度；要显式指定 `reasoning_effort`，须使用 `fork_turns="none"` 或有限历史轮数。其他环境按其真实工具定义执行，不照搬字段。
4. 已启动的一轮不能靠文字即时换档。成员先后完成不触发对同一批在途调用的强度修改；下一可配置批次重新按执行人数指派。主智能体没有本轮调参工具时，使用客户端或下一会话配置，不声称已经自动切换。
5. 区分“指派请求值”“已写配置”和“可核实的实际生效值”；没有运行时回执时只报告已知部分。工具不支持某档或覆盖时说明具体限制，不把继承值冒充已按规则设置。

Codex 的主智能体根配置键为 `model_reasoning_effort`；子智能体可以通过派发参数、`[agents]` 默认值或自定义成员文件影响强度。静态子智能体默认值不能表达本规则的两种人数情况，因此每次派发按批次核对；同时检查自定义成员配置是否覆盖请求值。[OpenAI 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)、[OpenAI 子智能体继承规则](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents)

部署本 Skill 安装的是指派规则，模型运行参数仍由实际调用设置。本机现有主智能体配置 `max` 符合单智能体执行情形，无需为本次规则改写配置。
